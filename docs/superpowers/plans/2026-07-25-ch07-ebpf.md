**2. BPF ISA**

BPF is a 64-bit RISC ISA with 11 registers (r0–r10):
- `r0` — return value from helper calls and from the program itself
- `r1–r5` — function arguments (clobbered across helper calls)
- `r6–r9` — callee-saved (preserved across helper calls)
- `r10` — read-only frame pointer; `r10 - 8` to `r10 - 512` is the BPF stack

`struct bpf_insn` (8 bytes per instruction):
```c
struct bpf_insn {
    __u8   code;       // opcode: class (3 bits) | source (1 bit) | operation (4 bits)
    __u8   dst_reg:4;  // destination register (0-10)
    __u8   src_reg:4;  // source register (0-10)
    __s16  off;        // signed 16-bit offset (memory/branch target)
    __s32  imm;        // signed 32-bit immediate
};
```

Key instruction classes: `BPF_LD` (load), `BPF_ST` (store), `BPF_ALU` (32-bit ALU), `BPF_ALU64` (64-bit ALU), `BPF_JMP` (branches + calls + exit), `BPF_JMP32`.

Instruction encoding examples:
```c
// 64-bit move: r0 = 42
BPF_MOV64_IMM(BPF_REG_0, 42)  // code=0xb7, dst=0, imm=42

// Helper call: call bpf_map_lookup_elem (helper #1)
BPF_EMIT_CALL(BPF_FUNC_map_lookup_elem)  // code=0x85, imm=1

// Exit: return r0
BPF_EXIT_INSN()  // code=0x95
```

Wide instructions (16 bytes): `BPF_LD | BPF_DW | BPF_IMM` loads a 64-bit immediate using two consecutive `bpf_insn` slots (second slot is a zero-filler). Used by `BPF_LD_MAP_FD` to embed a map fd.

**3. `struct bpf_prog`**

```c
// include/linux/bpf.h (simplified, Linux 6.9)
struct bpf_prog {
    u16             pages;        // number of pages allocated for this prog
    u16             jited:1,      // true if JIT-compiled
                    jit_requested:1,
                    gpl_compatible:1,
                    cb_access:1,

                    is_func:1,

    enum bpf_attach_type expected_attach_type;
    u32             len;              // number of bpf_insn instructions

    u8              tag[BPF_TAG_SIZE]; // sha1 of instructions (fingerprint)
    struct bpf_prog_stats __percpu *stats;

```

Key field: `bpf_func` points to either `___bpf_prog_run` (interpreter) or the JIT-compiled native code. After `bpf_prog_select_runtime()`, `bpf_func` always points to the JIT output on x86-64 (JIT is on by default).

`aux->used_maps[]` — array of map pointers referenced by this program (pinned alive while program runs).

**4. Verifier — `bpf_check()`**

The verifier in `kernel/bpf/verifier.c` performs abstract interpretation of every possible execution path:

1. **DAG check** (`check_cfg`): ensures no loops (only bounded loops via `BPF_JMP_BACK` with loop detector since Linux 5.3), unreachable instructions, too many instructions (BPF_COMPLEXITY_LIMIT_INSNS = 1,000,000).

2. **Type tracking** (`do_check`): each register carries a `struct bpf_reg_state` with a `type` field:
   - `NOT_INIT` — register not yet written
   - `SCALAR_VALUE` — unknown integer (arithmetic safe)
   - `PTR_TO_CTX` — pointer to program context (e.g., `struct xdp_md`)
   - `PTR_TO_MAP_KEY`, `PTR_TO_MAP_VALUE` — checked pointer into a map
   - `PTR_TO_STACK` — stack pointer (bounded)

3. **Memory access checks** (`check_mem_access`): every load/store must be to a `PTR_TO_*` with known alignment and bounds. `PTR_TO_PACKET` must be range-checked (the `data < data_end` idiom) before the verifier accepts the dereference.

4. **Helper call checks** (`check_helper_call`): each `BPF_EMIT_CALL` is checked against `bpf_helper_proto`, which specifies argument types and return type.

After passing, the verifier records `env->prog->aux->verified_insns` (number of instructions processed — the actual complexity cost, often much higher than `len`).

**5. JIT Compilation**

`bpf_prog_select_runtime()` calls `bpf_int_jit_compile()` on x86-64. The JIT:
1. Emits a standard x86-64 prologue: `push rbp; mov rbp, rsp; sub rsp, <stack_size>`
2. Maps BPF registers to x86-64 registers (BPF r6→rbx, r7→r13, r8→r14, r9→r15, r10→rbp for callee-saved; r1→rdi, r2→rsi, r3→rdx, r4→rcx, r5→r8 for args; r0→rax for return)
3. Emits native instructions for each BPF opcode
4. Calls `bpf_jit_binary_alloc()` to allocate an executable page via `module_alloc()`

JIT output is stored at `prog->bpf_func` (the actual x86-64 text). The interpreter path (`___bpf_prog_run`) is only used if JIT is disabled.

**6. Lifecycle**

```
bpf(BPF_PROG_LOAD, &attr, sizeof(attr))
  └─ bpf_prog_alloc()            # allocate struct bpf_prog + instructions
       └─ bpf_check()            # verifier (bpf_verifier_env)
            └─ bpf_prog_select_runtime()   # JIT compile
                 └─ fd installed in process file table
                    (bpf_prog_get_fd_by_id / prog lives until all FDs + refs released)

Attachment (e.g., SO_ATTACH_BPF):
  setsockopt(sk, SOL_SOCKET, SO_ATTACH_BPF, &fd, sizeof(fd))
    └─ sk_filter_trim_cap() → bpf_prog_get()   # bumps refcount
         └─ prog runs on every packet to that socket

Cleanup:
  close(fd)          # drops file reference
  detach socket      # drops sk_filter reference
  bpf_prog_free()    # called when refcount hits zero
```

**3. BPF_MAP_TYPE_HASH (`struct bpf_htab`)**

Hash map stores key→value pairs using an array of buckets with separate chaining:

```c
// kernel/bpf/hashtab.c (simplified, Linux 6.9)
struct bpf_htab {
    struct bpf_map  map;           // embedded base (must be first)
    struct bucket   *buckets;      // array of [n_buckets] struct bucket
    void            *elems;        // pre-allocated element pool (if !NO_PREALLOC)
    union {
        struct pcpu_freelist freelist; // per-CPU free list of elements
        struct bpf_lru      lru;       // LRU eviction (BPF_MAP_TYPE_LRU_HASH)
    };
    struct htab_elem *extra_elems; // per-CPU spare element for update-in-place
    atomic_t         count;        // current number of entries
    u32              n_buckets;    // power-of-2 bucket count
    u32              elem_size;    // sizeof(htab_elem) + key_size + value_size
    u32              hashrnd;      // random seed for jhash
};

struct bucket {
    struct hlist_nulls_head head;  // linked list of htab_elem
    union {
        raw_spinlock_t  raw_lock;
        struct {
            spinlock_t  lock;
        };
    };
};

struct htab_elem {
    union {
        struct hlist_nulls_node hash_node;
        struct {
            void                *padding;
            union {
                struct bpf_htab *htab;
                struct pcpu_freelist_node fnode;
                struct htab_elem *batch_flink;
            };
        };
    };
    union {
        struct rcu_head rcu;
        struct bpf_lru_node lru_node;
    };
    u32             hash;          // cached jhash of key
    char            key[] __aligned(8); // key bytes, then value bytes
};
```

Lookup path: `htab_map_lookup_elem` → `__htab_map_lookup_elem` → `htab_elem_from_hash_and_key()`. Walk the `hlist_nulls_head` for the bucket, compare keys with `memcmp()`. Lock-free with RCU on the read side; `raw_spinlock` on the write side per bucket.

**4. BPF_MAP_TYPE_ARRAY**

Array map is a fixed-size array indexed by `u32` key in range `[0, max_entries)`. No hashing, no bucket locking — the value at `array->value + key * elem_size` is accessed with `this_cpu_ptr` for per-CPU variants. Updates are done with `cmpxchg` or under a `bpf_spin_lock` for value-local atomic updates.

Performance characteristics: O(1) lookup with cache-line granularity; ideal for per-CPU counters and static config tables read from BPF programs.

**5. BPF_MAP_TYPE_RINGBUF**

Ring buffer for high-throughput event streaming from BPF programs to userspace. Introduced Linux 5.8 as a faster alternative to `perf_event_array`.

Key design decisions:
- Single producer (BPF program), single consumer (userspace `ring_buffer__poll()`)
- Memory-mapped directly into userspace (two `mmap` regions: one for the ring, one for the producer/consumer position pages)
- Lock-free: producer atomically claims a slot via `cmpxchg` on `producer_pos`; consumer reads `consumer_pos`

```c
// kernel/bpf/ringbuf.c (simplified)
struct bpf_ringbuf {
    wait_queue_head_t   waitq;
    struct irq_work     work;
    u64                 mask;              // size - 1 (size is power-of-2)
    struct page         **pages;
    int                 nr_pages;
    spinlock_t          spinlock ____cacheline_aligned_in_smp;
    atomic_t            busy ____cacheline_aligned_in_smp;
    /* shared with userspace via mmap: */
    unsigned long       consumer_pos __aligned(PAGE_SIZE);
    unsigned long       producer_pos __aligned(PAGE_SIZE);
    char                data[] __aligned(PAGE_SIZE);
};
```

BPF program usage:
```c
// In BPF C (compiled with clang):
struct event *e = bpf_ringbuf_reserve(&rb, sizeof(*e), 0);
if (!e) return 0;  // ringbuf full
e->pid = bpf_get_current_pid_tgid() >> 32;
bpf_ringbuf_submit(e, 0);
```

**6. BTF (BPF Type Format)**

BTF encodes C type information in a compact binary format, stored in the `.BTF` section of BPF ELF objects and also embedded in the kernel image (`/sys/kernel/btf/vmlinux`). It enables:
- **CO-RE (Compile Once, Run Everywhere)**: clang emits relocations (`__builtin_preserve_access_index`) referencing BTF type IDs; the BPF loader (`libbpf`) resolves field offsets against the running kernel's BTF at load time — no kernel header dependency at runtime.
- **Verifier type checking**: when a BPF program uses `bpf_probe_read_kernel_str()` on a BTF-typed pointer, the verifier can verify the access.
- **Map pretty-printing**: `bpftool map dump` uses BTF to pretty-print keys and values.

```bash
# Dump vmlinux BTF (kernel's type info):
bpftool btf dump file /sys/kernel/btf/vmlinux format raw | head -40

# Show BTF for a loaded BPF map:
bpftool map dump id <id>  # uses BTF to decode keys/values

# Verify CO-RE: check field offsets at load time:
bpftool prog load <prog.bpf.o> /sys/fs/bpf/test_prog
```

**7. bpf(2) Map Operations**

```c
// Create a hash map:
union bpf_attr attr = {
    .map_type    = BPF_MAP_TYPE_HASH,
    .key_size    = sizeof(u32),
    .value_size  = sizeof(u64),
    .max_entries = 1024,
};
int map_fd = syscall(SYS_bpf, BPF_MAP_CREATE, &attr, sizeof(attr));

// Update: key=1, value=42:
u32 key = 1; u64 val = 42;
attr = (union bpf_attr){ .map_fd=map_fd, .key=(u64)&key, .value=(u64)&val, .flags=BPF_ANY };
syscall(SYS_bpf, BPF_MAP_UPDATE_ELEM, &attr, sizeof(attr));

// Lookup:
u64 result;
attr = (union bpf_attr){ .map_fd=map_fd, .key=(u64)&key, .value=(u64)&result };
syscall(SYS_bpf, BPF_MAP_LOOKUP_ELEM, &attr, sizeof(attr));
```

**2. kprobe / kretprobe**

kprobes insert a software breakpoint (`int3` on x86) at the patched instruction:
1. `register_kprobe(kp)` replaces the first byte of the target function with `0xcc` (or uses jump optimization to a 5-byte `jmp` when trampolines allow)
2. On trap, the CPU calls `kprobe_int3_handler()` → `kprobe_handler()` → calls `kp->pre_handler`
3. For BPF: the handler is `kprobe_perf_func()` in `kernel/trace/bpf_trace.c`, which calls `trace_call_bpf(call, regs)` to run the attached BPF program with `struct pt_regs *ctx`

BPF program type `BPF_PROG_TYPE_KPROBE` receives `struct pt_regs *` as its context. Function arguments are accessed with `PT_REGS_PARM1(ctx)` through `PT_REGS_PARM5(ctx)` (architecture-dependent register names wrapped by macros).

Performance cost: kprobes add ~100–200 ns per hit because of the `int3` → trap → handler round-trip. Jump optimization reduces this when enabled.

**3. Tracepoints**

Tracepoints are static instrumentation points compiled into the kernel with `DECLARE_TRACE` / `DEFINE_TRACE`. They use a jump patch (NOP → `call __traceiter_<name>`) that is zero-cost when no probes are attached:

```c
// include/linux/tracepoint.h (simplified)
struct tracepoint {
    const char          *name;       // "net_dev_queue", "sys_enter_read", etc.
    struct static_key   key;         // jump key: NOP when disabled, CALL when enabled
    int (*regfunc)(void);
    void (*unregfunc)(void);
    struct tracepoint_func __rcu *funcs; // array of (func, data) pairs to call
};
```

`DECLARE_TRACE(name, proto, args)` generates:
- The `struct tracepoint __tracepoint_##name` in `__tracepoints` section
- `trace_##name()` inline function that checks `static_key_enabled(&__tracepoint_##name.key)` and calls the registered handlers
- `register_trace_##name()` / `unregister_trace_##name()` accessors

BPF programs attach to tracepoints via `BPF_PROG_TYPE_TRACEPOINT` with `perf_event_open()` and `PERF_TYPE_TRACEPOINT`. The tracepoint `format` file in `/sys/kernel/tracing/events/<category>/<name>/format` describes the payload fields.

**4. fentry / fexit**

fentry/fexit (introduced Linux 5.5) use BPF trampolines instead of kprobes:
1. The kernel generates a `struct bpf_trampoline` per `(fentry_ip, prog_type)` pair
2. The trampoline is a small JIT-generated stub that saves/restores callee registers and calls the BPF programs — much faster than a kprobe's `int3` round-trip
3. `bpf_trampoline_update()` in `kernel/bpf/trampoline.c` patches the target function's first instruction(s) to call the trampoline instead

fentry receives the function's arguments (via BTF type info — the verifier knows the parameter types from BTF and exposes them directly, no `PT_REGS_*` macros needed). fexit additionally receives the return value.

Performance: ~10–30 ns per hit (vs ~100–200 ns for kprobe), because there is no trap and the trampoline JIT avoids context switching overhead.

**5. Attachment Comparison**

| Type | Probe | Overhead | Arg access | Requires | When to use |
|------|-------|----------|------------|----------|-------------|
| kprobe | any kernel symbol | ~100–200 ns | `PT_REGS_PARM1–5(ctx)` | nothing extra | legacy, any kernel function |
| kretprobe | return of any symbol | ~200 ns | `PT_REGS_RC(ctx)` | nothing extra | return value tracing |

| fexit | BTF-visible function return | ~15–35 ns | typed args + return value | BTF, func in vmlinux | return + latency measurement |

**6. CO-RE (Compile Once, Run Everywhere)**

Problem: BPF programs compiled against one kernel's headers break when fields move in a newer kernel. CO-RE solves this:

1. `clang` with `-g` and `__builtin_preserve_access_index()` emits `CO-RE relocations` in the `.BTF.ext` ELF section, recording which BTF type ID + field name each access refers to.
2. At load time, `libbpf` (or the kernel's BPF loader) resolves each relocation by looking up the running kernel's BTF (from `/sys/kernel/btf/vmlinux`) and patching the instruction's immediate with the actual field offset.
3. If the field doesn't exist in the running kernel's BTF, the BPF program can be rejected at load time with a clear error message.

```c
// In BPF C (compiled with clang -g -O2 -target bpf):
#include "vmlinux.h"   // single header generated by: bpftool btf dump file /sys/kernel/btf/vmlinux format c

// CO-RE: compiler emits relocation for pid field, loader patches at runtime
pid_t pid = BPF_CORE_READ(task, pid);  // expands to __builtin_preserve_access_index
```

**2. XDP (eXpress Data Path)**

XDP attaches a BPF program at the earliest possible point in the RX path — in the NIC driver itself, before sk_buff allocation. This gives near-wire-speed packet processing.

```
NIC DMA → driver interrupt → xdp_frame (raw packet buffer)
                               └─ BPF program runs here (XDP hook)
                                    → XDP_DROP     (free the frame, zero copies)
                                    → XDP_PASS     (continue to netif_receive_skb, allocate sk_buff)
                                    → XDP_TX       (transmit back out the same NIC)
                                    → XDP_REDIRECT  (redirect to another NIC, CPU, or AF_XDP socket)
                                    → XDP_ABORTED  (bug; drops and increments error counter)
```

`struct xdp_md` (context for XDP programs):
```c
struct xdp_md {
    __u32 data;           // offset of packet start (cast to void * in BPF)
    __u32 data_end;       // offset of packet end
    __u32 data_meta;      // metadata area before data (for inter-prog communication)
    __u32 ingress_ifindex; // interface index
    __u32 rx_queue_index; // RX queue number
    __u32 egress_ifindex; // set for XDP_REDIRECT programs
};
```

The classic safety check pattern the verifier requires:
```c
void *data     = (void *)(long)ctx->data;
void *data_end = (void *)(long)ctx->data_end;
struct ethhdr *eth = data;
if ((void *)(eth + 1) > data_end)   // bounds check — required by verifier
    return XDP_DROP;
```

Three XDP operating modes:
- **Native** (`XDP_FLAGS_DRV_MODE`): runs in the driver before sk_buff; requires driver support (mlx5, i40e, ixgbe, virtio_net, veth, etc.)
- **Offloaded** (`XDP_FLAGS_HW_MODE`): runs on the NIC itself (Netronome SmartNIC); requires firmware support
- **Generic** (`XDP_FLAGS_SKB_MODE`): runs after sk_buff allocation in `do_xdp_generic()` in `net/core/dev.c`; slower, works on any NIC, no driver support needed

**3. TC (Traffic Control) eBPF**

TC BPF programs attach to the Traffic Control subsystem as classifiers (`cls_bpf`) or actions. Unlike XDP, TC programs operate on `struct __sk_buff` (a BPF view of `sk_buff`) and run on both ingress and egress paths — after sk_buff is allocated.

```
ingress:  NIC → netif_receive_skb → sch_ingress → cls_bpf (BPF program) → socket
egress:   socket → __dev_queue_xmit → sch_direct_xmit → cls_bpf (BPF program) → NIC
```

Attachment via `tc`:
```bash
# Attach BPF program to ingress:
tc qdisc add dev eth0 clsact
tc filter add dev eth0 ingress bpf obj filter.bpf.o sec tc direct-action
```

`struct __sk_buff` (BPF view of sk_buff):
```c
struct __sk_buff {
    __u32 len;            // total packet length
    __u32 pkt_type;       // PACKET_HOST, PACKET_BROADCAST, ...
    __u32 mark;
    __u32 queue_mapping;
    __u32 protocol;
    __u32 vlan_present;
    __u32 vlan_tci;
    __u32 vlan_proto;
    __u32 priority;
    __u32 ingress_ifindex;
    __u32 ifindex;
    __u32 tc_index;
    __u32 cb[5];          // 20 bytes of scratch space for BPF program communication
    __u32 hash;
    __u32 tc_classid;
    __u32 data;           // pointer to packet data
    __u32 data_end;
    __u32 napi_id;
    // ... additional fields
};
```

TC BPF return values: `TC_ACT_OK` (pass), `TC_ACT_SHOT` (drop), `TC_ACT_REDIRECT`, `TC_ACT_PIPE`, `TC_ACT_UNSPEC`.

**4. sockops and sk_msg**

- **BPF_PROG_TYPE_SOCK_OPS**: runs on socket events (connect, accept, SYN, ESTABLISHED). Used by Cilium to bypass Netfilter for local pod-to-pod traffic and to set TCP options for bandwidth management.
- **BPF_PROG_TYPE_SK_MSG**: filters/redirects messages sent via `sendmsg(2)` on a socket. Works with a `BPF_MAP_TYPE_SOCKMAP` to redirect traffic directly between sockets, bypassing the full TCP stack.

**5. Hook Point Comparison**

**2. Cilium — eBPF replaces kube-proxy**

How Cilium generates per-Service BPF programs:
- `BPF_MAP_TYPE_HASH` map: `cilium_lb4_services` maps ClusterIP:port → service entry
- `BPF_MAP_TYPE_ARRAY` map: `cilium_lb4_backends` maps backend ID → pod IP:port

Packet walk comparison (kube-proxy iptables vs Cilium eBPF):
- kube-proxy: traverse O(N) iptables rules for each packet
- Cilium: single hash map lookup O(1), no iptables traversal

**3. Tetragon — kernel-level security tracing**

Tetragon uses `BPF_PROG_TYPE_TRACING` (fentry/fexit) to attach to kernel security functions:
- `security_bprm_check`: intercept `execve` at capability check — gets binary path, creds, PID
- `security_socket_connect`: intercept TCP connections — gets remote IP, port, PID, cgroup
- `security_file_open`: intercept file opens — gets inode, path, flags

Events flow through a `BPF_MAP_TYPE_RINGBUF` to a userspace daemon that sends gRPC events to the Tetragon server, which exposes them as Kubernetes-aware security events (pod name, namespace, labels).

Enforcement: Tetragon can call `bpf_send_signal(SIGKILL)` from the BPF program to kill a process that violates policy — zero latency enforcement at the kernel level.

**4. Hubble — eBPF network observability**

Hubble sits on top of Cilium's eBPF datapath. Every Cilium TC BPF program emits events to a `BPF_MAP_TYPE_PERF_EVENT_ARRAY` when policy decisions are made (allow/deny, drop, redirect). The Hubble daemon reads these events and enriches them with Kubernetes metadata (pod name, namespace, labels) from the Kubernetes API.

Flow events show: source pod, destination pod, L4 protocol, verdict (FORWARDED/DROPPED/REDIRECTED), HTTP/gRPC metadata (if layer 7 proxy is enabled).

**5. Falco — eBPF driver alternative**

Falco (CNCF) supports an eBPF driver (`--driver ebpf`) that uses `BPF_PROG_TYPE_TRACEPOINT` on `sys_enter_*` / `sys_exit_*` tracepoints to capture system call events. This is the production-safe alternative to its kernel module driver. Events flow via `BPF_MAP_TYPE_PERF_EVENT_ARRAY` to the Falco userspace engine.

**What it demonstrates:** A single C file that uses the raw `bpf(2)` syscall directly (with `linux/bpf.h`) to:
1. Create a `BPF_MAP_TYPE_ARRAY` with `max_entries=8` (to store a counter per syscall "slot")
2. Assemble a minimal BPF program in bytecode that: increments `map[0]` by 1 on every invocation and returns 1 (accept) — using `BPF_FUNC_map_lookup_elem` + `BPF_FUNC_map_update_elem`
3. Load the BPF program with `BPF_PROG_LOAD`
4. Attach the program as a socket filter on a `AF_PACKET` raw socket (`SO_ATTACH_BPF`)
5. Send a small UDP packet on loopback to trigger the filter
6. Read back `map[0]` with `BPF_MAP_LOOKUP_ELEM` and print the counter

No libbpf, no clang required — only `gcc` and `linux/bpf.h`.

**Implementation details:**

The BPF program bytecode counts accepted packets by incrementing a map counter:
```c
struct bpf_insn prog[] = {
    /* r6 = r1 (save ctx ptr) */
    BPF_MOV64_REG(BPF_REG_6, BPF_REG_1),

    /* r1 = map_fd (BPF_LD_MAP_FD is two instructions: LD_DW + zero filler) */
    BPF_LD_MAP_FD(BPF_REG_1, map_fd),

    /* r2 = fp - 4 (key pointer on stack) */
    BPF_MOV64_REG(BPF_REG_2, BPF_REG_10),
    BPF_ALU64_IMM(BPF_ADD, BPF_REG_2, -4),

    /* *(u32 *)(fp-4) = 0 (key = 0) */
    BPF_ST_MEM(BPF_W, BPF_REG_10, -4, 0),

    /* call map_lookup_elem(map_fd, &key) */
    BPF_EMIT_CALL(BPF_FUNC_map_lookup_elem),

    /* if r0 == NULL, jump past increment (skip 5 instructions) */
    BPF_JMP_IMM(BPF_JEQ, BPF_REG_0, 0, 5),

    /* r1 = r0 (value pointer) */
    BPF_MOV64_REG(BPF_REG_1, BPF_REG_0),

    /* r2 = *(u64 *)(r1+0) (current count) */
    BPF_LDX_MEM(BPF_DW, BPF_REG_2, BPF_REG_1, 0),

    /* r2 += 1 */
    BPF_ALU64_IMM(BPF_ADD, BPF_REG_2, 1),

    /* *(u64 *)(r1+0) = r2 (write back) */
    BPF_STX_MEM(BPF_DW, BPF_REG_1, BPF_REG_2, 0),

    /* r0 = 1 (accept packet, return SK_PASS) */
    BPF_MOV64_IMM(BPF_REG_0, 1),

    /* exit */
    BPF_EXIT_INSN(),
};
```

Note: `BPF_LD_MAP_FD` is a macro that expands to two `bpf_insn` entries (a 16-byte wide instruction), so the array size must account for this. Use `ARRAY_SIZE(prog)` or count carefully.

Both sides print: map fd, prog fd, socket fd, the BPF_PROG_LOAD log (on error), and the final counter value.

The program must run as root (or with `CAP_BPF` + `CAP_NET_ADMIN`). Print a clear error with `strerror(errno)` if permission is denied.
